 Remaining differences are fixed-point rounding, not algorithmic
 error. The naive version keeps full double precision but truncates
 rather than rounds at each cast to int32 -- note the cast is
 (int32_t)(sum * ...) with no +0.5, so it biases toward zero and
 costs roughly half an LSB per pass. Loeffler rounds at every
 butterfly stage and defers its gain shift to after the column pass.
 The hardware rounds once per pass at its >>> 11 output stage.

 The LOEFFLER vs FPGA row is the most informative for your report:
 both are fixed-point with the same Q10 coefficients, so it isolates
 rounding strategy from the float-versus-fixed gap. They should agree
 to within a few LSB. JPEG quantisation divisors of 8-64 make that
 invisible in a reconstructed image.

 FIRMWARE VS SOFTWARE -- WHAT THE INLINE ASSEMBLY BUYS
----------------------------------------------------------------
 SW-LOEFFLER and FW-LOEFFLER run the identical algorithm: same
 stages, same Q10 coefficients, same rounding, same deferred gain
 shift. They differ in exactly one function -- the 3-multiply
 butterfly rotation -- which SW does in plain C and FW does in
 hand-scheduled ARM assembly. Any gap between them is the assembly
 and nothing else.

                   MEDIAN (ms)  PER BLOCK(us) PER BUTTERFLY(ns)
 SW-LOEFFLER (C)         3.413          2.844           29.6
 FW-LOEFFLER (asm)        3.871          3.226           33.6

 Butterfly rotations executed: 115200 (1200 blocks x 16 transforms x 6)

 RESULT: the assembly is SLOWER (0.88x, costing 0.458 ms per frame).

 This is a real and reportable outcome, not a mistake. At -O2 the
 compiler already schedules the two independent multiplies well,
 and an asm block is an optimisation barrier: the compiler cannot
 inline through it, cannot keep values in registers across it, and
 must materialise the coefficient struct into the constrained
 registers on every call. Hand assembly beats the compiler far less
 often on a modern toolchain than the folklore suggests.

 Worth checking before writing this up: compare the generated code
 for both with
     gcc -O2 -S -fverbose-asm dct_loeffler.c
 and count instructions in the rotation.

 Output equivalence: BIT-IDENTICAL across all 76800 coefficients.
 The assembly computes exactly what the C computes, so the
 speed comparison above is measuring the same work.

----------------------------------------------------------------
 INTERPRETATION
----------------------------------------------------------------
 Cost per 8-point 1D DCT:

   SW-NAIVE      64 cos() calls, 64 double multiply-accumulates
   SW-LOEFFLER   11 integer multiplies, 29 adds, plain C
   FW-LOEFFLER   same, with the rotation hand-scheduled in asm
   HW-FPGA       64 parallel MACs in fabric, 0 CPU multiplies,
                 but 16 bridge transactions of interface overhead

 SW-NAIVE should be far and away the slowest, and the reason is not
 the transform -- it is that cos() is recomputed from scratch inside
 the inner loop on every call. That is one libm call per coefficient
 per input sample, on a core with no fast transcendental unit. It is
 a correctness reference, not a serious contender; quote it as the
 baseline the other two are measured against.

 SW-LOEFFLER should beat it by two to three orders of magnitude:
 the butterfly factorisation removes the multiplies, fixed point
 removes the FPU, and the 3-multiply rotation with pre-computed
 simplified coefficients removes a third of what remains. The inline
 ARM assembly schedules the two independent multiplies into adjacent
 issue slots, so the rotation is limited by multiplier latency rather
 than by instruction count.

 HW-FPGA is the one to be careful about. Per 8x8 block it performs:

   16 one-dimensional transforms x (8 writes + 8 reads)
     = 256 lightweight-bridge transactions per block
     = 307200 transactions for this image

 Each read is an uncached round trip that stalls the CPU, while the
 transform itself completes in 3 clocks at 50 MHz (60 ns). The
 accelerator is therefore latency-bound on the interface, not
 compute-bound. If it loses to Loeffler, that is why -- it is not
 evidence that the DCT logic is slow, and the report should say so
 explicitly rather than presenting the number bare.

 This is the classic accelerator-granularity result: offload a unit
 of work this small and the interface cost exceeds the compute saved.
 The fix is a wider interface, not a faster transform -- DMA a whole
 64-pixel block across the bridge, run both passes in fabric with an
 on-chip transpose buffer, and read 64 coefficients back. That turns
 256 transactions into 2 bursts and lets the fabric's parallelism
 actually show. The 2D peripheral was the intended route to this.

 Caveat to state when quoting these figures: this measures a
 memory-mapped register interface driven from a user-space process,
 not the DCT core in isolation. Report it as end-to-end offload cost,
 which is both the honest framing and the more useful one.
